Note on set::iterator and set::const_iterator

The wiki template Template:cpp/container/assoc_note currently says:

The member types iterator and const_iterator may be aliases to the same type. Since iterator is convertible to const_iterator, const_iterator should be used in function parameter lists to avoid violations of the One Definition Rule.

This is a bit unclear, leading to Stack Overflow question https://stackoverflow.com/questions/56701128

Suggested new wording:

The member types iterator and const_iterator may be aliases to the same type. This means defining a pair of function overloads using the two types as parameter types may violate the One Definition Rule. Since iterator is convertible to const_iterator, a single function with a const_iterator as parameter type will work instead.

std::list and invalidating iterators

Recently, I had a very difficult to diagnose bug in my code happen because I wrote code that saved a value of myList.rbegin() and then added more elements with push_back(). I believed that this would be OK because the std::list main page says "Adding, removing and moving the elements within the list... does not invalidate the iterators or references." However, the value of the iterator I was saving was not correct, and I could not understand why.

As it turns out, this is because the guarantee about iterator invalidation only applies to forwards iterators. (see: https://stackoverflow.com/questions/10085570/why-does-a-push-back-on-an-stdlist-change-a-reverse-iterator-initialized-with )

I think that, to save people from falling into the same trap, the sentence on the std::list page should be changed to "Adding, removing and moving the elements within the list... does not invalidate references or forwards iterators."

The reason is given in the comments of the top answer: rbegin() actually references end() rather than prev(end()). end() is not valid in the first place, so it is not going to be invalidated anyway. Other reverse iterators still have the validation guarantee. Every time *rbegin() is evaluated, the value from prev(end()) is retrieved, meaning that dereferencing the reverse begin iterator always give you the “current” last element, regardless of whether you have stored that reverse iterator beforehand.
However, the caveat of using rbegin() still exist, and I added a note to address that. ✔ Done --Xmcgcg (talk) 19:15, 10 January 2024 (PST)

- parallel forward progress: guarantees that if a thread of execution makes a step, it will eventually make another step. Supports critical sections and locks, because the thread that has the lock will be scheduled again.
